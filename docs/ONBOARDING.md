# 零基础协作指南

这份文档面向一种具体的人：不会 `git pull` / `git push`，没装过 Git，唯一会做的是把 GitHub 仓库链接贴进 WorkBuddy，然后跟 Agent 说话。

结论先说：**你不需要会 git 命令，也能给这个项目提交特效。** GitHub 网页端本身就能改文件、开分支、提 PR，你在浏览器里点几下就完成了 git 的全过程；WorkBuddy 负责帮你读代码、写代码、解释报错。两条能力拼起来，完整流程是通的。

## 你实际要做的事

整个协作只有四个动作，都在浏览器和一个对话框里完成：

- 打开仓库网页，找到 `effects/` 目录，从 `effects/fire-transition/` 复制三个文件到你自己新建的目录。
- 在网页编辑器里改这三个文件的内容，保存时选「Create a new branch for this commit and start a pull request」。
- 在 PR 描述里写清楚：从哪段片子抄的、参数什么意思、你在本地跑出了什么结果。
- 等负责人 review。他合并之后，你的特效就进了主线。

`git` 在这四步里出现了，但你没打过任何一个 git 命令——网页替你打了分支、提交和推送。

## 第一天：三十分钟能做完的事

先不要写代码。第一天只做三件事，把环境认全：

- **看懂一个特效长什么样。** 打开 `effects/fire-transition/`，三个文件分别读一遍。`SKILL.md` 说明这个特效是什么、什么时候该用、有哪些旋钮、坏起来是什么样；`params.yaml` 是旋钮清单和默认值；`run.py` 里只有一个函数 `build()`，它把参数翻译成 ffmpeg 滤镜行。
- **跑一次自检。** 把仓库下载到本地（网页右上角 `Code` → `Download ZIP`，解压即可，不需要 clone），在解压出来的目录里执行 `python aicut.py validate-effect fire-transition`。看到 PASS 就说明环境和契约都对。这一步不需要素材、不需要 BGM、不出片。
- **看一份真实输出。** 执行 `python aicut.py params --effect fire-transition`，你会看到 7 个旋钮的当前值、范围和「影响什么」。用户跟你说的「火焰太暗」，就是这里面某一行的值太小。

三件事做完，你已经知道特效在这套系统里是什么形状了。

## 三种任务，按能力挑

不是每个人都要写代码。项目里有三档活，难度差得很远，按自己现在会的挑。

**收集档（不用改代码）。** 找参考片、拆镜头、写清楚「这个效果看起来是怎么做出来的」。产出物是一份提案，填进 `.github/ISSUE_TEMPLATE/new-effect.md`：效果叫什么、用户会怎么说它、大概需要几个旋钮、坏掉的时候画面是什么样。这一档最缺人，也最影响项目质量——特效的旋钮设计错了，后面写多少代码都是白费。

**参数档（只改两个文件）。** 在别人已经写好的 `run.py` 基础上，调 `params.yaml` 的默认值与范围，补 `SKILL.md` 的描述。这一档要用 `validate-effect` 自检，不需要理解滤镜语法，但要能说清楚每个数字变了以后画面哪里变了。

**滤镜档（写 `run.py`）。** 真正写 `build()`。这一档要求你能跑通一次真实渲染并给出 `qa.json` 的数字。写之前先读 `SKILL.md` 里的契约和 `CONTRIBUTING.md` 的边界，弄错契约的 effect 会被 `validate-effect` 直接拦下来。

## 三条不能破的纪律

这三条是分工能成立的前提，破了会直接影响别人。

- **只改自己那个目录。** `effects/<你的特效名>/` 之外的文件一律不动，特别是 `lib/`、根 `params.yaml`、根 `SKILL.md`。触发词写在你自己的 `SKILL.md` frontmatter 里，`catalog` 会自动汇总进路由表，所以加特效本来就不需要改共享文件。
- **不提交素材、BGM、字体和出片。** `.gitignore` 已经挡住了 `materials/`、`runs/`、`.env` 与视频文件，`docs/demo/` 是唯一例外。PR 里出现视频文件就是错的，review 会退回。
- **WARN 不许藏。** `qa` 报警了就在 PR 里把数字贴出来，说明你判断是真坏了还是可接受。删掉报警比报警本身更麻烦——负责人要靠这些数字判断改动有没有伤害节奏。

## 怎么跟 WorkBuddy 配合

Agent 在这套流程里的角色是「读代码 + 写代码 + 解释报错」，不是「替你按提交键」。有效的用法是这样：

- 把仓库链接贴给它，说「读一下 `effects/fire-transition/SKILL.md` 和 `run.py`，告诉我这个特效的参数是怎么进到滤镜里的」。它会给你一条从参数到画面的完整路径。
- 写新特效时，让它「照 `fire-transition` 的契约，帮我起草一个叫 XX 的 effect 的 `build()`，先只输出一个能通过 validate 的最小实现」。它能直接把三个文件的内容给你，你复制进网页编辑器。
- 报错时不要截图半句话，把终端里的报错**整段原文**贴给它（包括最后那行 `Error` 和上面的 `Command`）。少一行它就只能猜。
- 不确定某个参数改了会不会崩，让它「按 `params.yaml` 的范围帮我确认 3.5 这个值合法吗，会影响哪些镜头」。

反过来说，有三件事不要让它做：不要让它替你编造 `qa.json` 的数字，不要让它绕过 `validate-effect` 直接提交，不要让它改 `lib/` 去「适配」你的特效——需要改内核说明契约设计有问题，那是负责人的事。

## 提 PR 的时候写什么

PR 描述不用长，但四件事必须齐，缺一件 review 就会退回：

- **抄的是哪一段。** 参考片的时间区间，或者一句「原创」。
- **旋钮表。** 每个旋钮叫什么、范围多少、调大调小画面分别往哪走。
- **实测数字。** `qa.json` 里至少贴亮度均值、暗帧占比、重复帧占比、切点率四项，以及你判断 PASS 还是 WARN。
- **已知边界。** 这个实现在什么情况下会崩或者难看。留空等于没写，这一栏是给下一个改这个特效的人看的。

## 卡住了怎么办

按这个顺序试，通常第一步就解决了：

- 先跑 `python aicut.py doctor`，确认 ffmpeg 版本和滤镜能力，很多「效果出不来」是版本不支持某个滤镜，不是你的代码错。
- 再跑 `python aicut.py validate-effect <你的特效名>`，它会在不渲染的情况下把契约问题挑出来。
- 还是不行，把报错原文和 `doctor` 的输出一起贴给 Agent，说清楚你上一步想做什么。
- 最后才找人。找人时把这三样一起发：你执行的命令、完整报错、`doctor` 输出。

## 一分钟自检清单

提交前逐条对一遍，全过再点 PR：

- `validate-effect <名字>` 是 PASS，没有 TODO 残留。
- `catalog` 里能看到你的特效和你写的触发词，`conflicts` 显示 none。
- 你的改动只在 `effects/<你的特效名>/` 里。
- PR 里没有视频、音频、字体、`runs/` 产物和 `.env`。
- PR 描述里贴了 `qa.json` 的真实数字，或者明确写了「仅参数档，未出片」。
